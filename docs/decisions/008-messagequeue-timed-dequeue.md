# 008 — 为什么给 MessageQueue 加「带超时的等待」（并主动打破 core 零改动）

> 编号 008。由 007（CacheWriter 线程模型）派生 —— 007 决定 CacheWriter 要有
> 「攒够 N 条 **或** 等够 T 毫秒就写」两条触发路径，本篇决定第二条触发路径怎么实现。
>
> 状态：已决定。
> ⚠️ **本决策主动打破了「`src/core/` 零改动」的记录。**

---

## 问题

CacheWriter 的写线程需要一种等待语义：

> **「等到有数据，或者等够 `flush_interval`，哪个先到算哪个」**

而 `MessageQueue` 只提供了两种：

```cpp
bool dequeue(T& item);        // 阻塞，直到有数据或队列关闭
bool try_dequeue(T& item);    // 非阻塞，立刻返回
```

### 为什么现成的两种都不行

**用 `dequeue`（阻塞）** —— 死结：

```
t=0.000  写线程 dequeue → 睡着
t=0.050  来 1 条 → 醒，收进 batch_（1 条）
t=0.050  再次 dequeue → 又睡着
          ……从此没有新数据……
t=5.000  线程还在睡。batch_ 里那条已经等了 5 秒（远超 200ms）
         但没有任何人能叫醒它 —— 叫醒条件是「新数据来了」，而新数据恰恰不来
```

**`flush_interval` 想防的是"低负载"，而低负载恰恰是它失效的场景。**
这不是巧合，是逻辑上的矛盾。

**用 `try_dequeue` + sleep** —— 能 work，但退化成**轮询**：
一秒只来 2 条数据，线程也要每秒醒 1000 次去看一眼。

---

## 三个候选

| | 方案 | 代价 |
|---|------|------|
| (a) | `try_dequeue` + 短 sleep | 轮询：空转烧 CPU；sleep 粒度 = 延迟下限；不引入新线程、**不碰 core** |
| **(b)** | **给 MessageQueue 加带超时的等待** ✅ | **要改 core**（但可做成兼容加法）；零轮询、零额外线程 |
| (c) | 独立定时器线程 | 多一个线程；定时器与写线程会同时想 flush → 需加锁协调 |

**选 (b)。**

---

## 判据：这个改动该不该动 core？

「不改 core」**不是目标，是度量** —— 度量的是「核心只认抽象、不认具体实现」这个设计成立不成立。
M2 三次替换实现（Mock → Kraken → ws_stream.py 子进程）它都没破，这就是依赖倒置的实证。

但**把度量当成目标，就会为了保住数字而拒绝本该有的能力**。所以用三条判据检验：

### ① 是通用能力，还是业务特例？

**通用。** 证据：

- `std::condition_variable` **原生**就提供 `wait_for` / `wait_until` ——
  标准库不会为一个业务特例提供原生支持
- 不止攒批需要：任何「消费者可能长时间空闲、但需定期醒来」的场景都需要
- 换语言依然存在：Java 的 `BlockingQueue.poll(timeout)`、Go 的
  `select { case <-ch: ; case <-time.After(d): }` —— 都是同一个能力

### ② 是兼容加法，还是破坏性修改？

**可以做成零污染的加法：老接口一个字不改，只新增一个方法。**

```cpp
bool dequeue(T& item);                                    // 老，不动
bool dequeue_for(T& item, std::chrono::milliseconds t);   // 新，只加
```

现有所有调用点零影响 —— 这不是"污染"，是"能力扩展"。

> 接口语义难题（"超时了但队列没关"怎么表达？）也因此有了答案：
> **不要去动 `dequeue` 的返回值**（那才会破坏所有调用点），
> 让新方法自己定义语义即可 —— 见下面的接口设计。

### ③ 换个实现还在吗？

在。换成 `moodycamel::ConcurrentQueue`、Go channel、Java BlockingQueue，
攒批需要"带超时的等待"这件事依然存在。

**三条全过 → 该加。**

## 接口设计

```cpp
/// 带超时的取元素。
///
/// 返回值：true  = 取到了
///         false = 没取到（超时 或 队列已关闭）
///
/// 要区分这两种情况，调用方查 is_shutdown()（已存在，且单调）：
///
///     if (queue_.dequeue_for(item, interval)) {
///         batch_.push_back(std::move(item));
///     } else if (queue_.is_shutdown()) {
///         break;                          // 队列关了 → 收工
///     } else {
///         maybe_flush_by_time();          // 超时 → 检查是否该按时间 flush
///     }
```

**为什么用 `bool` + `is_shutdown()`，而不是新造一个 `enum class { Got, Timeout, Closed }`：**

- `is_shutdown()` 已经存在、且是单调的（设了就永远为真），检查它没有竞态风险
- 不引入新类型 → 老的调用方完全不受影响
- 语义足够清楚

## 对「core 零改动」记录的处置

**这条记录到此为止。** 但它作为度量的使命已经完成：

> **三次换实现证明了抽象成立 —— 指标完成了使命，就该退场，而不是被供起来。**

同时明确划清界限，避免下次滑坡：

```
❌ 坏的改法：为了某个下游方便，把 core 改成那个下游的形状
✅ 好的改法：补一个 core 本来就该有的通用能力，且做成兼容加法
```

**这次的额外价值**：它暴露了一个**真实的接口缺口** ——
`MessageQueue` 之前只被"一直有数据"的场景用（管道主链路），缺陷从未暴露。
**CacheWriter 是第一个"可能长时间没数据、但又必须定期醒来"的消费者。**

这和 M2 第二步「换第二个 `IWebSocketClient` 实现」是同一个道理：
**第二个消费者/实现，才能检验第一个接口设计得对不对。**
