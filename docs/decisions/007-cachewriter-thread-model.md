# 007 — CacheWriter 的线程模型：为什么用独立线程 + 自己的队列

> 编号 007。承接 004（为什么 Cache 用批量写入）—— 004 决定了"要攒批"，
> 本篇决定"攒批的代码跑在哪"。
>
> 状态：已决定，实现中。

---

## 问题

`CacheWriter` 要把管道处理完的数据批量写进 SQLite（见 004）。那么它该跑在哪？

看起来是个"线程放哪"的小问题，实际是**三个问题叠在一起**：

| # | 子问题 | 为什么重要 |
|---|--------|-----------|
| 1 | **fsync 的延迟谁承受？** | fsync 是毫秒级；而管道处理一条消息只要 ~92μs（M2 第三步实测）—— **差一个数量级** |
| 2 | **要维护几个"批"？** | 批越多 → 每批填得越慢 → 数据在内存等待越久才落盘 |
| 3 | **关闭时谁 flush 未满的批？** | 攒着的半批不写就丢（排空语义） |

**子问题 1 是决定性的。**

---

## 候选方案

### A. 每个 worker 线程各自攒批

```
Worker1 ─→ [批1] ─→ COMMIT
Worker2 ─→ [批2] ─→ COMMIT
Worker3 ─→ [批3] ─→ COMMIT
Worker4 ─→ [批4] ─→ COMMIT
```

表面上是"无锁、简单"，但有两个硬伤：

- **硬伤 1：fsync 直接落在 worker 身上。** COMMIT 时 worker 阻塞在 fsync 上，
  那条消息的处理时间从 92μs 变成约 1ms。平均值摊薄后不难看，但 **P99 会显著变差**。
- **硬伤 2：SQLite 同一时刻只允许一个写事务。** 所谓"无锁"是假的，锁在 SQLite 内部；
  多个 worker 并发 COMMIT 会互相阻塞，甚至返回 `SQLITE_BUSY`。

副作用：批变成 N 份 → 每份填满慢 N 倍 → **落盘延迟 ×N**。

### B. 独立线程 + 自己的队列 ✅ 选它

```
Worker1 ─┐
Worker2 ─┼─→ [CacheWriter 队列] ─→ CacheWriter 线程 ─→ [单一批] ─→ COMMIT
Worker3 ─┤
Worker4 ─┘
```

- ✅ fsync 由专职线程承受，worker 处理延迟不被污染
- ✅ 单一批 → 填得快 → 落盘延迟低
- ✅ 单个写连接 → 无 SQLite 写竞争
- ✅ flush 逻辑（batch_size / flush_interval / 关闭 flush）只有一份
- ❌ 多一个线程；多一次跨线程传递

### C. 共享批 + 锁（谁攒满谁提交）

- ✅ 单一批、无额外线程
- ❌ **提交的那个 worker 仍被 fsync 阻塞** —— 子问题 1 未解决
- ❌ **`flush_interval` 无人触发**：所有 worker 都在等数据时，没有线程能跑定时器，
  最终还是要引入一个线程 —— 绕回 B

---

## 决定性论证

**写盘是"档案"性质的操作，它的延迟不该拖累实时路径。**

| 环节 | 能容忍的延迟 |
|------|-------------|
| UI 刷新 | 卡 1ms 就看得出 |
| 行情处理 | 92μs 是基准，不能被拖到 1ms |
| **写入磁盘** | **晚 50ms 完全无所谓** |

这就是**快慢路径分离（fast path / slow path）**：高频、对延迟敏感的路径，
和低频、昂贵的 I/O 路径，必须分开。

> **让慢的那条路去等，而不是让快的路去等。**

---

## 结论

```
Workers ──┬──→ Publisher    （往内存/网络发布）
          └──→ CacheWriter  （往磁盘写）      ← M3 新增
```

**CacheWriter = 独立线程 + 自己的队列**，队列**直接复用 `MessageQueue`**：

```
Workers ──→ MessageQueue<待写数据> ──→ CacheWriter 线程
```

它和 `Publisher` 在结构上**对称**——都是 worker 的下游消费者，一个快、一个慢。

**背压策略：`DropOldest`。**

理由与 M2 第三步的 `PipelineBridge` 同源，但结果指向同一处：

| 场景 | 取舍 |
|------|------|
| `PipelineBridge` 的队列 | 宁可丢消息，也不能卡住 UI 线程 |
| `CacheWriter` 的队列 | 宁可丢历史 tick，也不能卡住实时 worker |

**两条都是同一个判断：不能让慢的东西拖住快的东西。**

---

## 反方观点（A 什么时候更优）

A 不是错的。它在这些条件下更合适：

- worker 数量 = 1（那 A 和 B 就是一个批）
- 写入量极低（每秒几条）—— fsync 的尖峰无所谓
- 极度不愿引入新线程

本项目场景是**高吞吐 + 多 worker**，A 的两个硬伤都会踩上。

## 🔴 实测修正（2026-09-24 补）

上面那句「**fsync 是毫秒级**」——**估高了。**

| | 原来估的 | 实测 |
|---|---|---|
| 单次 fsync 代价 | 毫秒级 | **256 μs**（DELETE+FULL，最贵的一档） |
| 攒批收益 | 10 ~ 1000 倍 | **16 ~ 165 倍** |

实测数据（2 万条，详见 LEARNING_LOG 的 M3 段）：

| 配置 | 每次 COMMIT | 攒批加速比 |
|---|---|---|
| WAL + NORMAL | 27.8 μs | 16.4 × |
| WAL + FULL | 58.3 μs | 34.5 × |
| DELETE + FULL | **256.4 μs** | **165.3 ×** |

**方向对，量级偏高 4~6 倍。** 现代 NVMe 比想象中快得多。

### 但这不推翻本决策

本决策的核心是**「fsync 的延迟不该落在 worker 身上」**，而不是「fsync 一定很贵」。
实测反而**强化**了它：

> **攒批之后，三种落盘策略的绝对性能被抹平了（0.034 / 0.034 / 0.031 秒）。**
> 也就是说，如果让 worker 同步写盘，**为了性能你就只能选 NORMAL**（放弃断电安全）；
> 而独立线程 + 攒批之后，**可以用 FULL，性能不变，持久性白拿**。

**独立线程换来的不只是"快"，还有"不必在持久性上妥协"。**
