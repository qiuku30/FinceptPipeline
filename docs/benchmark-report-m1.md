## 三、假设 vs 实测

跑 benchmark 之前立了四个假设，逐个对照数据验证：

**假设 1：轻载时三种策略无差异 — ✅ 成立**

rate=1000 档（消费能力 4444 msg/s 的 22%），三行数据几乎相同：dropped 全 0、queue_wait P50 均为 3~4us、wall 均为 10.00s。原因直接：**背压策略只在队列满时触发**，轻载下队列永远不满，策略分支根本没被执行过。推论：策略选型只对饱和场景有意义。

**假设 2：Block 的 queue_wait 随 rate 暴涨 — ✅ 成立**

Block 的 queue_wait P50 从 1000 档的 4us → 5000 档的 226,141us，暴涨约 5.6 万倍；10000 档继续涨到 226,301us 后**稳定在 ~226ms 高原**（高原值 ≈ 容量/消化速率 = 1000/4444 ≈ 225ms）。P95/P99 与 P50 高度接近（226~235ms），说明饱和态下延迟分布非常集中——**每条消息都等满一整个队列的排空时间**，这是 Block 的确定性代价。

**假设 3：DropOldest 的 queue_wait 有界 — ✅ 成立**

5000 档 P50=199,665us，10000 档 P50=99,914us——不仅没随 rate 暴涨，反而**降了一半**（机制见第四节）。P99 同样有界（213ms / 168ms），远低于同档 DropNewest 的 258ms。

**假设 4：DropNewest 的 queue_wait 最小 — ❌ 被推翻**

假设 DropNewest 因"拒绝新数据"而队列不满、等待最短。实测：5000 档 P50=225,114us、10000 档 P50=225,200us——与 Block 的 226ms 高原几乎完全一致，是三策略中最差（或并列最差）的。**三个假设成立一个推翻一个，推翻的这个恰恰是最有价值的发现。**

---

## 四、反直觉发现：为什么 DropNewest 的等待不是最短的

**直觉**：DropNewest 拒绝新数据 → 队列不会持续满 → 新数据等待短。

**数据**：DropNewest 在 10000 档的 queue_wait P50 = 225ms，与 Block（226ms）一致；DropOldest 只有 100ms。

**机制**：直觉错在只看了"入队口"，没看"队列里躺着的旧消息"。

DropNewest 的拒绝发生在入队口，但拒绝**不会清空队列**——饱和期间队列常驻 1000 条旧消息，每条被接受的新消息都要排在它们后面，等待时间 = 1000/4444 ≈ 225ms 的"排队高原"。它丢掉了新数据，却把路留给旧数据堵住：**被丢的数据没有为被留的数据争取任何好处**。

DropOldest 恰好相反：每次入队弹走一个队首，队首同时被两个力量消耗——Worker 取走（4444/s）+ 入队淘汰（10000/s），合计 14,444/s。新消息前面的"人头"以三倍速度消失，等待降到 ~100ms。**被丢的旧数据为被留的新数据清空了道路。**

一句话总结：**丢谁不重要，关键是队列里剩的是谁。** DropNewest 的队列里剩的是旧消息（堵路）；DropOldest 的队列里总是较新的消息（路是通的）。

这条发现的价值不仅在于选型，更在于方法：**benchmark 前写下的假设必须接受数据的检验，反直觉的结果往往是理解系统行为的最佳入口。**

## 五、结论与选型建议

**结论 1：轻载下策略无关紧要。** rate=1000 档三策略表现一致。若系统容量规划合理（消费能力 ≥ 峰值速率），背压策略永远不会出场。

**结论 2：Block 用"拖慢全局"换"零丢失"。** 10000 档 wall 从 10.23s 涨到 22.65s——背压沿着队列传导到生产者，整个管线以消费速率（4444 msg/s）运转，而非生产速率（10000 msg/s）。数据完整性拉满，代价是端到端时效性被牺牲。

**结论 3：DropOldest 是行情场景的最优解。** 三个论据：

1. **时间价值衰减**：行情数据价值随年龄指数下降，3 秒前的价格对交易者近乎无用；丢旧数据的损失远小于丢新数据。
2. **快照自愈**：行情协议周期性推送全量快照，被淘汰的旧 tick 可被快照覆盖修复，数据缺失不破坏状态一致性。
3. **新数据路径最短**：如第四节所示，淘汰机制为新鲜数据清路，饱和时 queue_wait P99（168ms）反而低于轻载到饱和过渡期的值，延迟上界可控。

**适用场景反推**（选型不是绝对的）：

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| 实时行情 tick | DropOldest | 时效 > 完整，本报告结论 |
| 交易委托 / 成交回报 | Block | 一条都不能丢，宁可慢 |
| 批处理任务流 | DropNewest | 处理速度优先，拒绝比积压好（任务可重试） |

## 六、局限性与后续工作

本报告的结论受以下条件约束：

1. **单一 Worker 数**：只测了 4 Worker。1/2/8 Worker 下消费速率不同，"排队高原"的高度随之变化，策略间的相对优劣可能翻转（如 Worker 数足够多时三策略全部退化为轻载）。M1 后续补横向对比。
2. **忙等模拟处理**：900us 的忙等是恒定耗时，而真实负载（JSON 反序列化、字段校验）耗时呈分布状，P99 会被长尾主导。接真实数据后需重测。
3. **固定速率生产**：真实行情是突发（bursty）流量，瞬时速率可达均值数倍。突发下的队列行为（尤其 DropNewest 的拒绝风暴）未覆盖。
4. **单次运行**：每组只跑了一次，未做多次运行取均值；并发调度噪声对 wall 和 P99 有影响。

后续工作（对应 PLAN.md M2/M3）：

- M2 接入真实 WebSocket 行情后，用同一 benchmark 框架重测三策略
- M3 CacheWriter 批量写入对比（单条 vs 100/批 vs 1000/批）
- 补充 Worker 数横向对比（1/2/4/8）
